## F10 本身的干扰

| F10 时间 | 详细捕获 armed 到完成 | 随后的秒级 FPS |
| --- | ---: | ---: |
| 14:23:42.368 | 约 419 ms | 22 |
| 14:23:45.088 | 约 481 ms | 21.7 |
| 14:23:55.336 | 约 386 ms | 28 |
| 14:24:19.566 | 约 403 ms | 24 |

这些是捕获请求到完成的墙钟区间，包含正常游戏执行、等待及诊断，不能全算作诊断独占耗时。
四次捕获各输出数千行；`DEBUG_FRAME_BEGIN` 到输出结束约 127–140 ms，也包括日志管道和采集器的影响。

源码证据：

- `src/runtime_debug.c::runtime_debug_mark` 同时请求线程快照、截图和完整渲染帧分析。
- `vk_frame_capture.cpp::Buffer` 在图形命令线程上读取并逐项格式化浮点常量；`Write` 同步输出渲染信息。
- `vk_rasterizer.cpp` 在 FrameCapture::Active 时停用纹理绑定 helper、部分准备结果和状态缓存。
- 第一份线程快照的命令线程调用链为 `DrawRecord -> BindResources -> BindBuffers -> FrameCapture::Buffer` 内联的 std::format；第二份顶部也在格式化代码。后两份展开不足，不能可靠确定调用链。
- 每次快照中的 5 个 JobWorker 和 2 个 FiosIO 线程均处于条件变量等待，两个可可靠展开的 VkRecorder 样本也在等待。但采样发生于详细捕获期间，不能推算正常游玩时的空闲比例或排除磁盘读取问题。

因此，F10 后更深的掉帧有很强的诊断干扰证据；F10 前的持续下降仍需独立优化。

## 分辨率、绘制量与当前安全限制

四个捕获区间记录了 4,216–6,078 次 draw、80–182 次 dispatch，包含 105–128 个图形 pass 和 25–69 个 compute 分组。
捕获均带 `truncated=1`（缓冲文本上限等会触发），且按显示缓冲写入划分边界，不应视为无遗漏、严格逐帧的基准。
主要颜色目标为 1920×1080，另有半分辨率和更小的后处理目标。
心跳的 3651×2054 是呈现尺寸，不能直接断言游戏主场景按该尺寸渲染。

`scripts/game_profiles.py` 设置 BB_DRAW_PIPE=0；`Rasterizer::DrawPipeWanted` 对 infamous 还有硬性保护。
这源于 Continue 转场曾暴露绘制流水线多个生产者访问 scheduler 的错误。
该限制减少了一层并行处理，但不代表所有图形线程都关闭；Vulkan recorder 仍存在。
不能仅改环境变量重新启用，必须先修复生产者所有权和提交顺序。

`VideoOut: vblank 60 Hz, frame limit 0 FPS` 是本次实际启动配置。
BB_FPS=30 不等于这里设了 30 FPS 呈现上限，不能把 20/30 FPS 的下降解释为正常锁帧。

## 按优先级实施的优化方案

1. **先降低诊断干扰并补齐计时。** 将日常 F10 改为轻量标记，保存标记前后的有界逐帧指标；完整常量/渲染帧捕获作为显式深度诊断。将常驻 GPU ring 写文件移出事件锁：现在每个事件都锁同一 mutex，Flush 还在持锁时写文件和重命名。优先保留崩溃诊断，使用有界队列、溢出计数及崩溃路径 try-lock，不能引入无界内存或阻塞。
2. **确定普通游玩的耗时分布。** 复用现有 BB_FRAME_STATS 的编译、上传、页保护、录制同步、host copy、GPU tick 等计时；改成有界、低频汇总，避免低帧率时每帧多行输出。增加按帧关联的 CPU 准备/提交及 GPU 时间，记录 p50/p95/p99、超过 33/50/100 ms 的帧数。当前会话未记录这些细项，不能倒推。
3. **按最大占比优化串行图形路径。** 如果资源绑定/缓存验证占主导，减少重复 descriptor 构建、范围查询及锁；如果 recorder/host copy 等待占主导，调整批量提交及等待位置。保持资源失效、GPU 写入可见性和命令顺序，不能为提速跳过正确性同步。
4. **修复后再恢复安全并行。** 只允许 command processor 提交 scheduler；准备线程输出不可变结果，由提交线程按序验证消费。覆盖 Continue、资源写后读、渲染作用域和关闭过程的竞争测试，再比较同路线性能。预期收益未测，不承诺百分比。
5. **按证据处理次要方向。** 若慢帧与新管线编译重合，再完善缓存/预热；若上传或页保护占主导，再做批量保护、暂存缓冲复用。当前缺页计数不区分软缺页与磁盘硬缺页，不足以认定内存不足。只有 GPU 时间明显占主导时才优先调整分辨率或图形效果。

## 验收方式和限制

同一版本游戏、存档、分辨率、窗口状态及行走/转向路线，先预热再比较；每次只变一个优化点。
分别保留无 F10 干扰和有轻量标记的结果，比较帧时间分布，而非只看 FPS 均值。
检查画面、输入、Continue 和资源加载回归；单元测试通过不等于性能提升或游戏完全正确。

## 本轮 Windows 多线程优化

本轮已完成并通过 Windows 构建：

- 保留 `DrawPreparation` 的异步扫描和资源读取，最多使用 8 个 worker；inFAMOUS 配置将其从
  `THREAD_PRIORITY_IDLE` 提升为 `THREAD_PRIORITY_BELOW_NORMAL`（`BB_PREP_PRIORITY=low`），减少
  准备队列落后导致的 GPU 线程串行回退。
- 在资源绑定前预取准备线程生成的只读纹理、采样器和缓冲区描述，不改变资源状态或命令顺序。
- 对连续图形绘制增加管线选择短路缓存；缓存命中前仍复核寄存器校验和、着色器二进制哈希和运动向量地址，
  不跳过着色器变化检查。
- 未启用 `BB_TEXTURE_HELPER`：已有 A/B 数据显示逐绘制 fork/join 在当前 CPU 上没有收益。
- 未恢复 `DrawPipe`：inFAMOUS 的 Continue 路径仍存在共享 Scheduler 生产者竞态，强行开启会重新引入崩溃。

本轮未重新启动真实游戏，因而尚未宣称实际 FPS 已提升。需要使用同一路线重新录制一次 F11 性能文件，比较
`bind_ns`、`pipeline_select_ns` 和超过 33/50 ms 的帧数，才能确认本轮优化对实际场景的收益。
