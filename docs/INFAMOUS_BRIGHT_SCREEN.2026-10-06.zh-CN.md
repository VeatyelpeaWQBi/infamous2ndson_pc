# 开场字幕之后亮屏停滞：用户会话分析

## 当前结论

程序在异常阶段仍持续执行图形操作和呈现画面；本次记录不支持“整个进程或 GPU 已经停止工作”的判断。
故障范围暂定为开场字幕结束后的场景/状态转换或渲染输出异常。尚未确定根因，也没有修复完成。
不能用持续呈现证明剧情、关卡逻辑仍在推进，也不能仅凭动画线程在等待就排除动画调度问题。

下方最初会话分析仅分析了用户已有记录。后续专项重现与修复见末尾追踪记录；亮屏仍未修复完成。

## 线程和图形证据

- F10 前后，呈现速率约 56–60 次/秒；采集器没有标记超过 15 秒不呈现的停滞。
  这是呈现调用速率，不是可玩性或画面内容变化的测量。
- MoviePlayer 停在 guest `0x290976`，MovieDecoder 停在 guest `0x28bd23`。
  对照现有游戏 ELF 反汇编及宿主符号，两者均位于条件变量等待路径
  （宿主 `native_cond_wait`，`runtime_mutex.c:74`），没有停在 FFmpeg 解码调用内。
  单次线程快照无法判断它们是否在等待正常工作、遗漏信号或状态切换。
- 主游戏线程的快照包含 guest `0x3ea09a` 的写内存指令，通过访问异常处理进入
  `Rasterizer::InvalidateMemory` / BufferCache / MemoryTracker 等待路径。
  GPU 缓存追踪使用内存保护；仅凭这条调用栈不能认定游戏发生了致命访问异常或死锁。
  后续 CPU 和呈现计数继续增长。
- VkRecorder 的快照位于 Vulkan 驱动和 `beginRendering` 路径。
  后续 GPU 操作继续增长，不能把该瞬时驱动等待当成永久卡死。
- 最后保存的 512 项 GPU 操作包含 132 次 draw、19 次 dispatch 和 1 次 present。
  仍有 1920×1080 及较小尺寸的渲染目标和多组着色器。
  这些操作表明渲染工作仍在发生，不足以判断场景内容是否正确。

分析用的当前 exe SHA-256 与会话 manifest 一致：
`cb74e32aaafc4cfff32570e3c6a3b1340923fa892319bac7ce8c6f8d3d73f783`。

## 已确认的兼容性疑点

1. **Stencil 比较与写入引用值冲突。**
   日志约 5195 次报告：
   `Stencil test requires test_val while ReplaceOp requires op_val; the stencil test will use op_val`。
   `vk_rasterizer.cpp::UpdateDepthStencilState` 确实在存在 ReplaceOp 时使用 `op_val`
   作为 Vulkan 的共同引用值，即使游戏的 stencil 比较需要不同的 `test_val`。
   这是源码可确认的语义近似，可能影响遮罩/合成。
   警告从 21:31:08 就出现，早于异常转换，不能仅凭重复警告认定它就是亮屏根因。
2. **转换阶段的浮点 denorm 模式不完整。**
   `emit_spirv.cpp::SetupDenormFlushMode` 在 GPU 不支持请求模式时只警告，未添加相应执行模式。
   本次首次警告出现在转换前，但日志没有给出对应 shader 哈希或中间像素结果。
   目前只是候选问题，尚无证据证明它造成过曝、NaN 或亮屏。
3. **状态切换/资源就绪仍需查证。**
   GameState 创建、存档挂载及 GPU 工作量下降在时间上相邻。
   当前日志不记录每次视频解码返回值、视频帧计数、资源就绪状态或条件变量信号关系，
   所以无法区分缺少场景输出和游戏状态未继续推进。

开场文件 `art/movies/cutscene/v_vor_opening_no_text.bsf` 存在且可读取，大小 107709640 字节。
使用现有 MSYS2 FFprobe 可识别 H.264、1920×1080、yuv420p。
这排除了“该文件不存在或现有 FFmpeg 完全无法识别视频头”的情况，
不等于完整视频逐帧验证通过，也不证明游戏调用的 Videodec ABI 和调度无误。

初始化列出的设备格式/扩展警告是能力查询；没有证据证明每一种不支持的格式都被当前场景使用。
DLSS 缺失、旧 shader 缓存项被跳过也不能据此当作亮屏根因或要求补装依赖。

## 本次 F10 记录的限制及后续调查顺序

1. **先补齐异常画面证据。** 当前诊断只在宽不超过 1920、高不超过 1080 时截图。
   本次窗口放大后为 3651×2054，超过上限，F10 的 `capture-next` 到结束仍未消费。
   `last-frame.bmp` 时间是 21:31:07，不能当作 21:32:37 的异常画面。
   Presenter 根据 swapchain 尺寸调整呈现帧；GPU 操作仍显示 1920×1080 渲染目标，
   因此较大的呈现尺寸本身不证明游戏内部渲染分辨率异常。
   后续诊断应在保留截图大小上限的同时，对较大呈现帧缩小读回，并记录截图时间及原始尺寸。
2. **冻结标记时的 GPU 证据。** 当前 `gpu-recent.txt` 每秒覆盖一次，最后内容晚于 F10 约 4.5 秒，
   只能作为临近阶段的证据，不能称作精确的 F10 GPU 快照。
   后续应单独保留标记时的有界操作快照。
3. **补充低频状态/视频计数，再选择修复。** 对视频 create/decode/flush、有效输出帧和失败码做有界统计；
   在标记时关联 stencil 比较/写入值、shader 哈希及中间目标读回。
   这样才能判断应修复状态同步、视频接口，还是遮罩/后处理。
4. **按定位结果验证。** 使用合成单元及 Vulkan 测试覆盖确定的错误；
   最终由用户正常启动并测试字幕后的转换，不能用单元测试通过宣称亮屏已解决。

## 后续专项追踪（北京时间 22:26–23:23）

已修复两个可复现的独立兼容错误，但二者修复后亮屏仍存在：

- `session-20261006-222550-619965` 在 22:26:11.657 对
  `art/cache/graffiti_a8_family.xpps` 的 1 MiB 定位读取返回 Win32 998、errno 14。
  GPU 追踪可能在读文件前重新保护接收页，内核文件读取无法使用用户态异常处理解保护。
  Windows 读取现改用最多 1 MiB 的宿主缓冲，再在用户态复制到游戏地址；覆盖只读页、部分读取、
  EOF、定位读取及偏移错误的原生测试通过。不能把该错误描述为实际硬盘损坏。
- 捕获到 stencil compareMask=4、writeMask=0、test=4、op=0、passOp=Replace。
  关闭写入时必须用比较引用值，现已修复；对应 256 种 stencil 值的比较回归通过。

关闭图形缓存及预取等优化的对照运行仍亮屏。整帧捕获显示主场景存在几十次几何绘制，
绘制阶段深度为 GreaterEqual、清除值 0、未开启正反面剔除。
完成帧检查点的深度和部分 GBuffer 九处小块采样均为零，最终显示帧则有有限非零颜色。
采样只覆盖 9×8×8 像素，不能视为整幅图的穷尽检测。

进一步核对缓存顶点着色器 `0x7c5220cb_0.spv`：每个物体常量有 53 个 dword，
第 21–24 项确实参与 gl_Position 四个分量的平移加法，捕获值为 NaN。
这不同于把未使用字段中的整数掩码误读为浮点异常。采样绘制的 instance offset 为 0。

23:18–23:19 的硬件观察点还原出以下 CPU 数据路径（为该游戏 ELF 的相对地址）：

1. `0x1a32ae` 从物体记录加载平移分量，XMM13 为 NaN/NaN/NaN/1；
   `0x1a34d3` 把投影变换的平移结果写入 GPU 常量。
2. `0x19910f` 把已有 NaN 平移从源记录复制到渲染队列。
3. `0x1995ec` 写入源物体记录，XMM3 为 NaN/NaN/NaN/1。
   上游 `0x199474` 在世界变换与场景参考位置之间做减法，目前正区分两侧数据来源。

因此已确认至少一条场景几何路径在 CPU 阶段就产生无效位置；尚未确认首次产生 NaN 的原因，
也未证实这条路径是亮屏的唯一原因。不得通过直接把 NaN 改成零来宣称兼容完成。

观察点按需启用，最多保留每个地址 64 个不同指令命中，进入现有有界会话日志。
诊断构建使用已有 CLANG64/Python，17 项 CTest 单元测试和 4 项实际 Vulkan 测试通过。
这些通过结果不代表真实游戏已进入下一步骤。

## 亮屏修复验证（北京时间 2026-10-07 02:14）

`session-20261007-021345-1710b1` 已越过原来的亮屏，实际呈现德尔辛站在广告牌前的
3D 场景，并显示繁体中文「垂直握住無線控制器」提示。证据为该会话
`last-frame.bmp`（02:14:29）以及持续增长的呈现计数；这次运行未启用硬件观察点。

继续追踪前述 NaN 后，确认相机父级骨骼的姿态来自 `0x892a80–0x894886`
动画解码函数。该函数使用 `[rsp-0x50]` 到 `[rsp-0x8]` 的临时数据，同时执行
需要本机通过 Windows 异常模拟的 AMD EXTRQ 指令。Windows 不保留 System V red zone，
异常交付可破坏这些常量，最终使动画平移、相机原点和投影坐标成为 NaN。

`scripts/infamous_cpu.py::protect_animation_leaf` 对此函数作以下局部修复：

- 显式栈帧由 `0x3d8` 扩大到 `0x458`，同步修改唯一退出路径。
- 将 10 处负 RSP 操作数移至已保留的栈内空间，并保持 16 字节 SIMD 对齐。
- 调整 8 处传入栈参数读取；普通栈内局部变量保持相对位置。
- 增长的指令通过新增 4 KiB 可执行页跳转，不移动原始分支及 RIP 相对引用。
- 先验证 CUSA00309、程序 SHA-256、完整函数 SHA-256、原始指令及补丁不重叠。
  只修改准备后的 `boot-linked.bin`；原始游戏文件不变。

本轮修复后，已观察的相机原点从 NaN 恢复为
`(10601.140625, -20216.70703125, 2462.30322265625, 1)`，与实际恢复的场景画面相吻合。
此前 stencil 和文件读取修复仍保留，但仅这次动画栈保护使此复现路径越过亮屏。

新增原生行为测试在真实 EXTRQ 执行前后检查普通局部变量、栈下变量、对齐 SIMD 数据
及传入栈参数。另以确定性栈下覆盖模拟宿主异步用栈，验证未保护版本失败、保护版本成功；
不能把这项模拟覆盖描述为每一次 EXTRQ 都必然破坏栈。还覆盖修改后程序指纹拒绝写入。
首轮补丁的 SIMD 对齐错误已由该测试补充覆盖。

本轮验证结果：

- 130 项 Python/原生用例完成验证。沙箱内 3 项 Tcl 菜单测试受限，沙箱外通过；
  完整运行中 1 项 EXTRQ 测试的子进程超时，单独复测通过（没有放宽超时时间）。
- 2 项独立原生测试通过：手柄输入，以及受保护页面上的文件读取。
- 17 项 CTest 单元测试通过。沙箱内 CTest 子进程返回 DLL 加载失败 `0xc0000135`，
  同一测试直接执行通过；申请范围限定的沙箱外 CTest 调用后 17 项全部通过。
- 本轮无跳过的选中用例；继续排除历史 Linux/AppImage 打包模块。
  Vulkan 集成测试本轮未重跑，前轮 4 项通过；本轮变更仅涉及游戏准备时的 CPU 栈补丁。
- 记录：`out/infamous-animation-tests.log`、`out/infamous-animation-retest.log`、
  `out/infamous-animation-ctest.log`。主日志保留首次超时结果，复测结果独立记录。

此结论限于「开场后亮屏」这一阻塞。当前进入了体感操作提示，现有手柄实现的姿态字段仍为
单位四元数，尚未提供体感输入；因此不能据此宣称 Xbox 手柄可完成该操作，也不代表后续游戏
流程已经全部验证。
