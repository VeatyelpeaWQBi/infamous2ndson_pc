# 最新游玩低帧率与转场变暗：分析和本轮修改

## 实际数据

分析对象为用户实际会话 `out/CUSA00309/debug/session-20261007-212801-c57129`。
读取了 active/status/manifest、runtime 日志、输入标记、GPU 心跳和完整 F11 CSV；没有后台重启游戏。
本轮游戏正常退出，退出码 0，未报告致命异常。

F11 为北京时间 21:28:18.230 至 21:33:00.568，共 15,556 帧、282.304 秒，文件报告丢帧 0。
两次 F10 都已收到，分别在 21:32:55.575 和 21:32:57.259；tick_ms 为 27563843、27565531。
每个标记前后一秒的呈现速率分别约 31.47 和 31.00 FPS。
末一分钟整体约 47.04 FPS；全片约 55.10 FPS 包括启动/轻量阶段，不能作为实际游玩平均帧率。

按 interval_ns >= 33,333,333 分组，共 755 个慢帧。

| --- | ---: | ---: |

整段编译计数为零。因此这段持续低帧率不能靠增加着色器预编译直接解决。
图形命令 CPU 和绑定开销有明确数据支持；等待 GPU 的原因仍需区分设备执行时间、队列依赖和提交方式。
CPU 时间来自 Windows GetThreadTimes，具有量化粒度，应按多帧平均理解。计数按 flip 区间采样，
不保证异步工作严格归属于同一游戏帧。绑定、采样器、CPU 和等待指标有包含/跨线程关系，不能直接相加。
当前没有 GPU 执行时间，不能宣称显卡瓶颈已完全排除。

纹理集合缓存全片命中 10,301,801 次，未命中 1,034,987 次，约 90.87% 命中；
其中 1,806,703 次复用来自此前已实施的无关注册变化重新验证。这项优化已在游戏中触发，
但本次帧率说明它还不足以保证 60 FPS。

## 本轮已实施的引擎优化

1. 纹理集合哈希原来强制最低位为 1，使 32,768 槽的缓存只能使用奇数槽。
   改为只把零哈希转换为非零值，保留其他哈希的全部位；缓存空间不增加。
   合成的 50,000 个集合、两轮相同访问中，占用槽数由 15,601 增至 25,648，重复命中由 2,312 增至 10,888。
   这是缓存分布和命中改善，不是游戏 FPS 测量。
2. 相同纹理子范围连续只读时，原来反复遍历每个 mip/layer 的状态。
   增加最近只读请求的记忆；相同范围、布局和阶段可直接复用检查结果。
   写入、不同访问和后备图像切换会失效；第一次读写转换仍走原有 Vulkan 屏障逻辑。
   实际引擎函数、320 个子资源、10,000 次连续读取的微基准为 2.864 ms → 0.024 ms，
   此为未开启性能统计时的一次测量，不代表全帧耗时降低同样倍数。
   随后在与 F11 一致的 BB_PERF_STATS=1 下复测为 2.914 ms → 0.057 ms，
   日志 `out/image-state-benchmark-perf-enabled.log`；验证新增统计未抵消这个函数的改善。
   新增 image_read_memo_hits、image_subresource_checks 两列，以后用真实录制验证命中和绑定耗时。
   启动前设置 BB_IMAGE_READ_MEMO=0 可回到旧的逐次检查方式，方便同场景对照。

没有放宽 GPU 读写同步，没有开启此前不安全的绘制流水线，也没有修改游戏文件、正式存档或降低画质。
当前数据尚不能判断重复子资源检查在游戏纹理绑定耗时中的占比；两项实际代码优化的整局收益待测。

## 转场变暗与 F10 的诊断缺口

这次 F10 有时间和数字记录，但旧版轻量模式没有请求画面；旧截图路径还限制源尺寸为 1920×1080。
当前呈现尺寸为 3651×2054，因此无法从历史记录补出变暗前后的图像或色彩状态。
已有 F11 也不包含游戏曝光参数或图像，不能据此确认是游戏曝光/fade、历史纹理、资源同步还是呈现色彩转换。
没有把推测作为已确定原因，也没有强制 gamma 或删除必要屏障来掩盖变暗。

新版默认 F10 会请求当前帧和约三秒内三张后续帧，附带 gamma、HDR、sRGB 输入、源像素格式和编码像素平均亮度。
最高接受 4096×2160 源图，后台缩小到最多 1920×1080；循环保留八组截图约 48 MiB。
最多两个待处理 GPU 暂存帧，4K 时约 68 MiB；GPU 复制和分配仍有开销。
等待 GPU 完成、像素转换和文件写入转到低优先级线程，避免原来渲染线程等待截图完成。
深度线程/命令捕获仍须显式请求；普通 F10 不会启用这些明显干扰性能的操作。

新增指标增大了诊断历史，回归检出 Windows 栈溢出；已将相关大块历史副本放到堆上，分配移出渲染生产者锁。

## 验证与下一步验收

构建使用已有 Windows CLANG64 工具链，无依赖下载。构建日志 `out/image-state-optimization-build.log`。
测试入口 `test.bat --gpu`，结果记录于 `out/image-state-optimization-tests.log`。
145 项 Python 测试、独立原生检查、23 项 CTest 单元检查和 8 项真实 Vulkan 集成检查通过；
无失败或跳过，历史 Linux/AppImage 包装模块按 Windows 项目规则排除。
新增检查覆盖屏障等价性/写后读/子范围变化、缓存分布、4K 截图转换与元数据、GPU timeline 完成前不读取像素、
后台截图提交和退出清理，以及轻量 F10 的截图请求。

仍需要相同工厂室内/室外路线的真实游戏 F11 对照，按相同区间比较帧间隔、绑定耗时和新缓存命中；
不能用全片启动阶段的平均值代替游玩性能。发生变暗时按 F10，随后保持测试至少三秒，
可把实际画面与呈现色彩状态对应起来。当前尚未验证本轮游戏 FPS 提升或稳定 60 FPS，变暗根因也尚未确定。
