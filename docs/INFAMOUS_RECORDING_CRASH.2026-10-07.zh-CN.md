# 长录制异常退出、恢复与性能分析

会话：`out/CUSA00309/debug/session-20261007-175224-e22b56`。
测试时间：北京时间 2026-10-07 17:52:24–17:56:15。
分析用户实际会话，未重新启动游戏，未修改游戏文件或存档。

## 1. 退出原因

17:56:15.385：`SaveDataDialog opened; completed immediately (no dialog UI yet)`。
17:56:15.635：`STOP: first unsupported PS4 import`，随后明确输出
`API: sceSaveDataDialogGetResult`。
完整导入身份：`yEiJ-qqr6Cg#libSceSaveDataDialog:1#libSceSaveDataDialog:257#F`。
调用者 guest offset：`0x1e6431`，首参数：`0x9cfa40`。

`src/runtime_services.c` 注册了存档对话框 Initialize / Open / UpdateStatus / Terminate，
但没有注册 GetResult。`src/probe.c::unresolved` 遇到该导入时报告并调用 `_exit(20)`。
这与 status.json 的退出码 20 完全对应，是本次退出的直接原因。
该退出路径明确不运行析构函数，避免未停止的 GPU、音频和 guest 线程执行析构；因此录制线程没有机会正常收尾。

本次日志没有 Host fault、Guest fault、Vulkan device lost 或驱动崩溃记录。
退出前采集器仍记录约 59–61 FPS；F11 没有 STOP 标记。不能把此次退出归因于 F11 停止操作或显卡性能。
GetResult 兼容实现尚未在本次任务中补齐，下一次触发同一对话框仍可能退出。

### 常见掉帧：绘制量和资源绑定

| 分组 | 每帧 draw 均值 | 命令线程 CPU 均值 | BindResources 均值 | host copy 等待均值 |
| --- | ---: | ---: | ---: | ---: |
| 小于 20 ms | 2,348 | 8.47 ms | 4.09 ms | 0.52 ms |
| 大于等于 33.33 ms | 5,357 | 25.67 ms | 14.10 ms | 0.70 ms |
| 超过 50 ms 且无编译 | 7,396 | 37.91 ms | 22.87 ms | 0.75 ms |

慢帧集中在绘制工作增多及 CPU 资源绑定耗时增加，host copy、录制线程等待都相对小。
录制末段第 180–200 秒窗口平均仅约 34.3 / 32.1 FPS，BindResources 均值约 17.18 / 17.39 ms，
这些窗口没有编译帧；随后第 200 秒起的最后窗口恢复约 58.6 FPS、绑定约 3.42 ms。
不能只优化编译便宣称解决所有掉帧。

### 短时长卡顿：运行中编译

16 帧超过 100 ms，其中 15 帧伴随编译；最长帧约 517.60 ms，记录到约 499.82 ms 编译耗时。
另两帧约 467.88 / 334.42 ms，编译分别约 440.63 / 318.66 ms。
这些帧的图形管线选择计时很小，而编译计时包含 compute 与 graphics，
提示需要优先区分计算管线/着色器编译和图形管线编译，不能只预热 graphics 管线。

另有一帧约 234.87 ms，CPU 时间约 203.13 ms，未记录编译，绑定仅 3.97 ms。
该帧主要耗时不在现有细项中；本次无对应 F10 栈快照，不能杜撰具体函数根因。

所有帧时间来自 guest flip 的宿主时钟，计时项可跨 flip、可嵌套。
Windows 命令线程 CPU 计时呈 15.625 ms 台阶，单帧精度有限；分组均值适用于趋势比较。
GPU tick 等待是 CPU 等待量，不等于 GPU 执行时间；当前没有 GPU timestamp，不能完全排除 GPU 负载。
这条测试路线与前次 23 秒路线不同，不能据此计算之前多线程改动的性能收益。

优先处理：补齐存档对话框生命周期；将计算和图形编译分开计时并优化预热/缓存；
减少资源绑定重复验证与全局缓存失效；对未覆盖的 CPU 慢帧进一步取样。

## 4. 自动收尾改造

采集器现在监听 F11 START / STOP，按秒将帧数据写入会话专属旁路缓存。
所有录制缓存合计每会话最多 32 MiB，避免无限增长；达到上限后停止追加，仍保留常驻环形诊断，
恢复时明确报告缺口。正式恢复文件会另外占用相应空间。
游戏渲染线程不新增文件写入、队列等待或子进程。

游戏退出后（包括异常退出和仍在录制的正常退出），采集器汇总缓存与轮换帧文件、
去重、校验，生成 performance-recording-N.csv 和汇总。
成功校验已被最终文件完整覆盖的缓存后才删除；失败保留缓存，并写 recording_errors。
已有正常录制不覆盖。采集器自身也被强制结束时不能立即收尾，但旁路缓存仍可供手动恢复。

针对旋转去重、损坏尾行、完整性、冲突保留、磁盘上限和真实子进程 `_exit(20)` 的回归已通过。
后者确认只启动一个合成进程，自动生成正式录制及汇总并清理已验证缓存，未启动真实游戏。
最终执行 `test.bat --gpu`：143 项 Python/原生用例、18 项 CTest 单元用例、4 项 Vulkan 集成用例全部通过；
无失败、错误或跳过。日志：`out/recording-recovery-tests.log`。本轮修改采集器脚本，无需重新编译游戏程序。
