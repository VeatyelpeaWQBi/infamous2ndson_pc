  `153a5aa7f6b6be0e547d46719b793cb5145571d7`；复用已授权下载的本地源码快照，没有新增依赖。
- [Bilibili 文章](https://www.bilibili.com/opus/1256550763349409795)，标题为“可能是全球首发，从根源破解血源诅咒移植PC以及模拟器的显存泄露问题，基本告破！！！”；已读取正文。
- 本地测试目标仍为 CUSA00309，原始游戏、正式存档只读，所有代码修改在运行时引擎。

## 可借鉴的实现与风险

| AYOUB 实现 | 对本地的意义 | 本轮处理 |
|---|---|---|
| `MemoryTracker::GetCpuVersions` / `BufferCache::sync_memos` | CPU 未修改已上传范围时，复用驻留缓冲区，省去页面扫描和驻留范围查询 | 独立实验开关 `BB_BUFFER_SYNC_MEMO=1`，默认关闭；检查两个 4 MiB 区域版本及当前 arena，排除写绑定、纹理别名、热页面 |
| 上传 worker 批量合并页保护 | 把部分保护及复制工作移出图形命令线程 | 本地已有异步复制；页保护仍受锁与读写权限时序约束，需要完整的 deferred-protect 协议，不能只把 VirtualProtect 异步执行 |
| 第二回读队列 / 异步计算队列 | 有机会缩短游戏 CPU 等待反馈的延迟 | 需要每范围最后写入 tick、跨队列依赖、快照所有权追踪；不能只新增队列，否则可能读旧粒子状态 |
| `readback_write_discard` / 可选 write-merge | CPU 覆盖旧 GPU 数据时有机会省去无用回读 | 丢弃整个页可能丢失同页其他粒子数据；write-merge 默认关闭，不能直接照搬丢弃策略 |
| `DynamicState::BindCache` | 减少 Vulkan 重复管线、push constant、描述符绑定 | 本轮窄化为 `BB_PIPELINE_BIND_MEMO=1` 图形管线实验；在录制线程比较实际命令顺序，原始命令缓冲区逃逸及新缓冲区开始均失效，场景 resampler 也走统一入口；不跳过描述符、常量或 draw |
| 异步管线编译并跳过未完成 draw | 降低冷编译等待 | 会暂时漏画，本地不以少画粒子换取帧率 |

已移植的粒子同步、legacy 浮点数规则和按页验证异步回读见
`INFAMOUS_REFERENCE_COMPARISON.2026-10-08.zh-CN.md`。AYOUB 的文档并不构成本机完整效果原生 4K 60fps 的证据。

## 文章可以提供什么

文章的可取方向是识别游戏内部资源的真实寿命。PS4 统一内存里的子分配器可能释放或重用一块资源，
却不解除映射整块系统内存；模拟器因此不能只用系统 unmap 判断资源死亡。
作者对血源 `FreeUntil(mark)` 等分配器路径的分析属于血源证据，不能套用地址或分配器类型到 inFAMOUS。
文章关于显存泄漏与 TDR 因果关系的判断没有本地复现，不能当作当前低帧率的定论。

进一步工作应只读分析 inFAMOUS 自己的分配/释放路径，关联 F11 中的资源注册、地址重用、GPU 完成 tick
及显存预算；确认资源死亡且 GPU 不再使用后再回收。不能按固定时间粗暴删除仍被 GPU 写过的缓存。
目前的既有测试没有显存压力回收日志，不能据此认定需要扩大缓存上限。

## 16 GB 显存的使用边界

本机 `nvidia-smi` 确认 RTX 4090 Laptop GPU、16376 MiB。查询时游戏未运行，使用量 3972 MiB，
这个数字不代表游戏的峰值占用。缓冲区已经使用 device-local 稀疏驻留，纹理缓存已经按 Vulkan 显存预算调整回收阈值。

长期保留不变纹理/几何数据和复用 GPU 产物可以减少搬运；游戏逻辑、解压、绘图指令转译仍需 CPU。
粒子系统由 GPU 写入、CPU 随后读取的反馈不会因为增加显存而消除等待。预装整包资源还缺少运行时描述符、
格式、别名和寿命信息，不能把磁盘资源包当作可直接绑定的 Vulkan 资源。

## 本轮验证

只读缓冲区实验构建成功：188 项 Python、33 项原生及 17 项真实 Vulkan 回归通过。
第一次 Vulkan 回归有纹理回收测试超时：生产统计报告清零计数后，旧测试还检查它；早于 CRT
错误输出配置执行的断言又等待弹窗。将统计报告放到测试检查之外，并提前配置 stderr 后，单项和全部
17 项 Vulkan 复验通过。生产回收逻辑未修改，首次失败日志保留。

当前存档，1080p，45 秒预热、静止/转镜头各 15 秒，同一程序只改变只读缓冲区实验开关：

| 模式 | 静止 FPS / p95 ms | 转镜头 FPS / p95 ms |
|---|---|---|
| `BB_BUFFER_SYNC_MEMO=0` | 30.42 / 44.12 | 31.83 / 40.60 |
| `BB_BUFFER_SYNC_MEMO=1` | 30.53 / 42.99 | 30.83 / 42.67 |

命中约 1612/1395 次每帧，但命令线程 CPU 23.76→24.44 ms、21.24→21.75 ms，整帧同步时间基本不变。
这个单次对照没有证明收益，不启用默认值。大量绑定仍涉及经常被 CPU/GPU 更新的页面。
图片已检查，火焰/烟气主体存在；图像随动画变化不应逐像素相同。输入匹配、原始存档不变及正常退出已验证。
报告与 F11 汇总：`out/reverse-engineering/ayoub-sync-memo-{off,on}{,-metrics}.json`。

游戏运行期间一次显存查询约 8921 MiB（系统总量，包括其他程序），GPU 利用率 61%、图形时钟
2355 MHz；另一阶段 8798 MiB、76%、2340 MHz。这是瞬时样本，不是平均利用率或游戏独占占用。

最新用户会话 `session-20261009-202052-2317b8` 正常结束；F11 共 1640 帧，没有丢帧。
平均命令线程 CPU 26.35 ms/帧、资源绑定 10.58 ms、游戏线程回读等待 21.29 ms、GPU 命令线程回读等待
2.68 ms、缓冲区上传约 13.91 MB/帧。不同线程/包含关系的时间不能相加；这些证据更支持减少每帧工作
和同步依赖，而非把显存装满。当前这份录制没有开启细分 buffer profiler，其 0 值不代表同步没有成本。

图形绑定实验最终 Windows 构建成功；188 项 Python、34 项原生、17 项真实 Vulkan 回归通过，
没有跳过。第一次新增场景覆盖断言超时，因为 NVIDIA 的硬件 blit 路径没有调用待测绑定入口；
强制测试走 portable stencil 绘制路径，并把断言错误输出到 stderr 后，单项及全部 51 项 CTest 复验通过。
Windows CTest 的公共环境现在追加，不覆盖原来各测试自身的开关。
当前存档、同一最终程序的图形绑定实验，45 秒预热、每阶段 15 秒：

| 模式 | 静止 FPS / p95 ms | 转镜头 FPS / p95 ms |
|---|---|---|
| `BB_PIPELINE_BIND_MEMO=0` | 33.07 / 40.13 | 32.58 / 40.16 |
| `BB_PIPELINE_BIND_MEMO=1` | 30.34 / 43.05 | 31.40 / 40.84 |

开启后每帧约 5730/4715 次重复管线绑定被消除（约 88%），但无实际帧率收益。
命令线程 CPU 22.54→23.32 ms、21.01→21.21 ms。没有把这些单次负面结果解释为全部差距都由
该开关引起；也不把消除调用次数当作优化成功。报告和 F11 汇总在
`out/reverse-engineering/ayoub-pipeline-memo-{off,on}{,-metrics}.json`。画面检查主体效果仍存在，
输入匹配且正式存档不变，正常退出。两个实验均保留为显式实验开关，普通启动默认关闭。

## GPU 区间和原始着色器对照

单独开启 `BB_GPU_PROFILE=1` 进行诊断，两个缓存实验关闭。
测得 FPS 29.58/31.15，不能拿它和不采集 GPU 时间的轮次直接比较优化收益。
GPU timestamp 标记会改变 render pass 分段，区段包含同步、复制及队列等待，不是纯着色器执行时间。
后期样本的提交间隔区段约 6.5–10.4 ms/帧；这不是显存不足的证据，也不是单个着色器成本。

已导出和反汇编下列热点的原始 GCN，仅读取原始包/已有运行时捕获；输出不写回游戏。

| 计算着色器 hash | 后期区段时间约 ms/帧 | 调度次数约 /帧 | 当前 Vulkan 变体 |
|---|---:|---:|---|
| `75453dfa` | 1.0 | 41 | 239 loads、9 atomic、0 control barrier |
| `29f590f3` | 0.84–0.96 | 41 | 230 loads、9 atomic、0 control barrier |
| `4274add5` | 0.90–0.93 | 47 | 208 loads、9 atomic、0 control barrier |
| `3839cbea` | 0.87–0.92 | 41 | 230 loads、9 atomic、0 control barrier |
| `ce1675e0` | 1.38–1.45 | 1，120×68 groups | 309 loads、6 atomic、34 control barriers |

前四组每次只启动一个 64-lane workgroup；原始指令有大量 buffer loads、stores、atomic min/max/add，
其中三组含 GDS append，但没有普通 LDS load/store。不能将它们归咎于 LDS 控制屏障。
`ce1675e0` 原程序有 3 个显式屏障和共享数据读写；转译后增加同步，可检查其冗余但不能直接删除保正确性的屏障。
静态指令数不是耗时，区段标记也不证明该时间全来自对应着色器。

本轮发现原分析工具只读取散装 `.spv`，没有读取引擎实际优先使用的 `all_shaders.vkpack`；
这既漏掉热点，也可能分析过时散装版本。现在按原生 BBVKPK01 格式只读解析集中包，验证源包 XXH3、
条目校验和、版本、边界、名称、重复项和尾部数据；集中包存在时不以散装文件补缺，符合引擎行为。
使用系统已有 `libxxhash.dll`、`spirv-val.exe`、`spirv-dis.exe`，没有新依赖。
实际包有 2659 个条目，五个热点的十个变体全部通过 Vulkan 1.3 SPIR-V 验证。

原始记录：`ayoub-gpu-interval-profile{,-metrics}.json`、`ayoub-gpu-interval-profile-segments.txt`；
原始 GCN/反汇编及当前 SPIR-V/验证报告：`out/reverse-engineering/ayoub-profile-shaders/`。
最终测试：190 项 Python、34 项原生、17 项真实 Vulkan，通过且无跳过；历史 Linux/AppImage 模块按项目规则排除。
隔离测试目录约 494.4 MiB，保持在已授权的 512 MiB 内；未安装新环境、改动正式存档或游戏源文件。

## 下一轮实施需要验证的方向

1. 对上述 min/max 原子操作确认返回值是否被使用、各 lane 的目标地址是否相同，再评估 subgroup 聚合。
   必须覆盖混合地址、分歧控制流、活跃 lane 和返回值语义，不能未经证明把 64 次调用合成一次。
2. 上传与页保护需建立独立 worker 的所有权及最新权限校验，再移出图形命令线程。
3. 缩短粒子反馈回读的队列依赖需追踪真实最后写入 tick；不能以缓存或预测值代替反馈。
4. 资源预热优先针对当前/相邻场景及已确定的静态数据，同时识别真实释放时机；不能只增加缓存容量。

以上方向尚未宣称实现或达到 50–60 FPS；本轮两项运行时实验没有证明正向收益。
