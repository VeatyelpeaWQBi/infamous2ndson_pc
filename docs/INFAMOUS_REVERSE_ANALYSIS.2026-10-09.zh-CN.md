# 游戏程序与引擎对照分析

输入始终只读：CUSA00309 01.07，主程序 SHA-256 为
`2d1ca79630d7bbe6fa29575f59aa7996d43071d74ac8e4f7d40137967d9039ab`。
Ghidra 12.1.4 使用现有 JDK 21.0.10。数据库和导出结果在 `out/reverse-engineering`，本轮约 120 MiB；不写回游戏目录。

## 反编译结果与证据范围

导入已有的 `out/CUSA00309/eboot.elf`，按照 PS4 x86-64 GCC ABI 分析。
自动分析识别约 27,539 个函数，在本轮 180 秒限额后停止；部分函数存在重叠修复警告。
已成功导出热点周围 20 个函数的 C 伪代码、汇编及调用关系。不能宣称整个游戏完成反编译，或所有自动推断的类型准确。

导出脚本：`scripts/ghidra/InfamousHotFunctions.java`。
结果：`out/reverse-engineering/hot-functions/functions.tsv` 和各地址 `.c` / `.asm`。
没有开发符号，以下用途由指令和调用关系推断，保留原始地址作为依据。

| 游戏函数 | 可直接验证的行为 | 对照引擎路径 |
| --- | --- | --- |
| `003f3ed0` | 读取对象 `+0xf0` 指针所指数据的 `+4` 字段，复制到 `+0xe8` 所指结构的 `+8`；再安排后续工作 | `Rasterizer::ReadMemory` → `BufferCache::ReadMemory` |
| `003edef0` | 等待同步后，遍历两组链表，逐个调用 `003f3ed0` | 连续的 GPU 反馈读取，不是单独某条着色器的执行成本 |
| `003ee160` | 沿 `+0xb0` 链接遍历对象并调用同一热点 | 同类连续读取的另一入口 |
| `0016dd50` | 原子预留计数并限制容量，生成两段数据地址，记录步长 `0xb0` / `0x50` | 反馈影响后续数据处理与提交，不能通过忽略回读来优化 |
| `001695e0` | 轮询完成字段，期间调用 `0053b2b0(0x32)` | 游戏自身存在同步逻辑 |
| `0053b2b0`（补充反汇编） | 使用 `rdtsc` 忙等到计算出的时间点 | 不应误认为 Windows 睡眠接口的固定延时 |
| `001691e0` | 生成命令、管理环形缓冲区，最终经 `009858a0` 导入跳板提交 | SELF 重定位 `00d9eb48` 对应 NID `bX5IbRvECXk`，引擎映射为 `sceGnmDingDong` |

`sceGnmDingDong` 的 `WaitGpuIdle()` 在此处等待提交锁，不等同于每次等待 Vulkan GPU 完全空闲，不能仅凭函数名称删除。

## 原始着色器与 SPIR-V

离线读取 `all_shaders.xpps`，依据 `OrbShdr` 元数据及代码起始指令的回指验证，取得 215 个可确认代码起点的程序。
目标火焰 VS/PS `bbd2d927` / `24dad4be` 在该包中。六个靠前的计算任务未在该包中找到，已从运行时实际使用的原始 GCN 捕获；不能声称所有游戏着色器都在这个包里。

引擎增加了对已从 Vulkan 缓存恢复程序的原始代码导出，仅在显式设置 `BB_DUMP_SHADERS=1` 时执行。
`image-compat-test --gcn-disassemble INPUT OUTPUT` 复用引擎自身 GCN 解码器。
LLVM gfx700 反汇编入口不支持该子目标，本轮尝试失败；已停止使用该入口，不将空输出当作成功。

`scripts/analyze_particle_shaders.py` 只读提取原始代码、统计对应 SPIR-V，并调用已有 `spirv-val` / `spirv-dis`。
八个目标、九个缓存变体均通过 Vulkan 1.3 SPIR-V 校验。结果为 `out/reverse-engineering/shaders/report.json`。

六个计算任务都包含九个 SPIR-V 原子操作，没有额外 `OpControlBarrier` / `OpMemoryBarrier`。
例如 `8a4ea184` 原始 GCN 约 400 条指令，包含缓冲区原子加、六个原子极值操作及 `DS_APPEND`；转译中的原子操作数量与原始用途相符。
SPIR-V 指令总数包含声明、类型及控制流，不能直接与 GCN 数量相除后当成性能膨胀倍率。

首轮分段 GPU 时间线约 32.5 ms/帧，其中约 19.6 ms 属于提交间空档，目标火焰绘制段约 0.28 ms。
这些间隔含同步、传输和排队，不能视为纯着色器耗时，也不能证明其他烟气剧情没有 GPU 瓶颈。

## 对照实验及本轮修正

当前隔离检查点为码头场景，1920×1080；静止及转镜头。已检查实际截图，不能与早期车祸现场跨场景比较。

- 集中到同步点预取：41.74/38.06 → 34.96/33.19 FPS，没有收益，未作为默认。
- 完全关闭预取：30.64/32.38 FPS；同时会关闭已知回读窗口学习，不能视为仅移除 GPU 复制的单因素实验。
- 同程序 500 微秒预取间隔试验：31.94/34.84 → 34.25/34.33 FPS；静止略升、转镜头略降，尚无可重复收益，默认间隔仍为 0。

测量修正：GPU 分析器取消等待查询结果；按提交时间线完成状态回收查询槽，没有可用槽时跳过诊断，避免重置在途查询。
真实 GPU 回归测试覆盖未提交的查询耗尽、恢复和安全复用。

实际阻塞修正候选：异步回读中的 `TryPrefetchedReadback` 原先仍在 GPU 命令线程调用 `scheduler.Wait`。
`BB_ASYNC_PREFETCH=1` 将已有预取快照及其确切 GPU tick 转交请求者，由游戏读线程等待；不重复发出该复制。
缓冲区所有权转移后，后续预取使用独立存储；按页版本仍拒绝新写入，只有 GPU 拥有的字节可以发布到 backing。
该候选需完成实际游戏对照后，才能决定是否默认启用。

同一程序实测 `BB_ASYNC_PREFETCH=0/1`：静止 34.46→31.20 FPS，转镜头 34.99→34.21 FPS。
静止回读等待约 8.72→13.63 ms/帧，图形命令 CPU 时间约 18.33→18.26 ms/帧。
虽然避免了 GPU 命令线程直接等待该快照，但没有测出端到端收益，默认保持关闭。

下一轮细分缓冲绑定：同步约 3.6–4.0 ms/帧，arena 绑定约 6,600–7,000 次/帧。
`BB_GPU_DIRTY_REUSE=1` 为精确回读模式提供候选短路径：在区域锁内确认 CPU 未修改且所有页已经由 GPU 持有时，
不重复扫描上传和更新保护；其他区域仍持锁完成上传及所有权转换。绘制、GPU 写入范围及快照失效追踪没有省略。
已完成同程序的 A/B/B/A 复测（FPS，静止/转镜头）：

| 顺序 | 复用开关 | 静止 | 转镜头 |
| --- | --- | ---: | ---: |
| 1 | 关 | 32.72 | 34.31 |
| 2 | 开 | 35.54 | 34.74 |
| 3 | 开 | 37.16 | 32.31 |
| 4 | 关 | 39.55 | 37.97 |

同步耗时在首组静止测试为 3.342→3.321 ms/帧，转镜头为 2.644→2.729 ms/帧，
没有与假设一致的稳定下降。A/B/B/A 结果也没有可重复的帧率收益，因此已撤除该实验实现及专用辅助函数。
原始报告与 F11 指标保存在 `out/reverse-engineering/dirty-reuse-*.json`。

下一项单因素试验：`BB_READBACK_SPECULATIVE=0` 只停止提前复制及其额外提交，保留读取位置学习、
批量回读、页版本检查和精确回读。此前 `BB_READBACK_PREFETCH=0` 同时关闭学习，不能独立判断提前复制的代价。

该试验已经完成，同程序、同存档、45 秒预热、每段 15 秒：

| 策略 | 静止 FPS | 转镜头 FPS | 静止回读等待 ms/帧 | 转镜头回读等待 ms/帧 |
| --- | ---: | ---: | ---: | ---: |
| 提前复制开启，4096 KiB 窗口 | 38.41 | 39.46 | 5.26 | 5.52 |
| 仅关闭提前复制 | 29.09 | 35.18 | 13.92 | 9.24 |
| 提前复制开启，512 KiB 窗口 | 37.78 | 39.74 | 6.80 | 5.46 |

静止回读量从约 8.19 MB/帧降到 1.44 MB/帧，但帧率没有提高；等待增加抵消了复制量下降。
保留现有提前复制和 4096 KiB 默认窗口。原始报告分别为 `speculative-on/off*.json`、`window512*.json`。
这些场景没有着色器编译，约 4,500 draw/帧，图形命令线程约 17–20 ms CPU/帧；
绑定耗时是其子项，不能把它们直接相加。

代码审查另发现 `IT_SET_PREDICATION` 未实现，`PixelPipeStatDump` 使用合成遮挡计数。
新增默认关闭的 `BB_OCCLUSION_TRACE=1`，按 1、2、4、8… 次命中输出，先判断游戏是否使用这些路径。
不能只凭兼容性缺口就认定它导致当前帧率，也不能用伪造“不可见”结果减少绘制。

验证：`speculative-build.log` 构建退出 0；`speculative-tests.log` 包含 176 项 Python、
31 项原生单元、16 项 Vulkan 集成测试全部通过，无失败或跳过。
Linux/AppImage 历史打包模块按 Windows 项目规则排除。后续诊断改动另行构建验证。

切换已存在的 `seed-current` 车祸/火焰存档（与码头的 seed 不同，禁止跨场景算收益）：
1920×1080 静止 31.85 FPS、转镜头 33.98 FPS，截图确认火焰和浓烟主体存在。
运行时确认 `PixelPipeStatDump` 命中超过 16,384 次，未见 `SetPredication` 命中。
证据：`visibility-current.json`、`visibility-current-metrics.json`、`visibility-current-packets.log`。

短时硬件观察查询地址 `0x10f97cd008`：只捕获引擎清零、合成计数写入及快照时的复制，
尚未定位到游戏 CPU 直接读取点。工具原有日志固定使用“write”字样，但本次模式是 reads and writes，
必须结合指令判断读写。`bb-probe.exe+0x1988ac` 已符号化到 `liverpool.cpp` 的合成计数写入。
没有 CPU 读取记录不能证明查询未使用，GPU 着色器也可能读取这些结果。
完整证据保留为 `visibility-watch-runtime.log`；该轮受观察点影响，禁止当作性能对照。
自动比较工具现已拒绝带 `BB_HW_WATCH` 的报告。

## 查询消费者与下一轮资源绑定

关联诊断找到计算着色器 `cfe61c5c`，slot 1 直接绑定查询结果的 2048 字节区域。
大范围原始描述符重叠只是候选，不能证明读到了查询；后续诊断已改为使用实际映射裁剪后的范围。
该程序在 `all_shaders.xpps` 中，原始 GCN 1124 字节，SHA-256 为
`1e9d6dfd6a457bc47d70dbd56a857b1acfa5a09017389869182123d7d979e879`。
对应 SPIR-V 通过 Vulkan 1.3 校验，有 70 次 load、两处条件 store，没有循环、原子或屏障。
原始 GCN 与 SPIR-V 都显示：累加查询结束计数、减去开始计数，
对两组差值转换浮点并相除，输出一个比例；分母为零时输出零。
快照为 1×1×1 工作组、64 个本地线程。尚未证明该比例控制大量几何剔除，不能据此承诺帧率收益。

675 个直接绘制、1235 个 dispatch 没有零规模记录。这些是有限快照样本，不能外推为所有帧。
测试了只检查有效 CPU backing 的单次间接绘制，但候选没有产生有效跳过，现已撤除。
也不能把 CPU 保护标记单独当成 GPU 间接参数的最新值证明。

本轮工具故障分别为 LLVM 22 优化崩溃、测试链接时的缺失符号，以及 MSYS2 Python 3.14
在预算统计中的 `_TAIL_CALL_CACHE` 内部错误。重试及重编译已有 Sirit 构建产物后链接成功；
没有更换或升级编译器。Python 入口修正为先读取已配置的持久系统/用户路径，

该恢复报告采用独立 schema，不能作为完整的正常优化比较输入。

调用方原有 GPU 读写屏障、间接参数访问追踪和页版本校验仍执行。

## 自动 CPU 诊断管线

`tools/win32_cpu_profile.c` 只访问经可执行路径和进程创建时间校验的进程，
选择 `shadPS4:GpuCommandProcessor`，暂停线程仅用于复制控制寄存器，恢复后才输出。
不改变优先级、亲和性、寄存器或游戏内存。原生自测验证线程恢复及身份拒绝。
`scripts/profile_runtime_cpu.py` 限定当前隔离会话，拒绝结束、PID 不匹配、程序改变及覆盖已有数据。
该工具的快照是近似指令观察，上一间隔有 CPU 进度不代表取样瞬间未在等待；不能换算为精确 CPU 耗时。

入口：`runtime-benchmark.bat run --allow-test-data --checkpoint current --cpu-profile --warmup 90 --seconds 15`。
采样在预热中自动执行 5 秒，输出通常约 20 KiB，计入原 512 MiB 隔离预算。
保存模块映射及 LLVM 内联信息；只有所有采样区间都不与测量重叠时，FPS 才能用于比较。
手动首轮发生重叠，`cpu-profile-current-run.json` 已标记诊断专用；自动轮确认没有重叠。

自动轮：322 个观察，187 个上一间隔有 CPU 进度，63 个在引擎；
其余主要为 ntdll、win32u。这些数量不是 CPU 时间百分比。
依据系统 DLL 导出位置，观察包含等待、内存保护和 `RtlQueryPerformanceCounter`，
没有单个引擎函数占主导。证据：`cpu-auto-sample.csv`、`cpu-auto-sample-functions.json`。

下一单因素候选 `BB_BIND_TIMER_STRIDE=16`：五类高频绑定/选择计时使用独立的伪随机 1/16 抽样，
按比例估计总耗时，避免固定周期漏掉交替 VS/PS。帧间隔、线程 CPU 时钟、操作计数及同步等待仍精确记录。
默认仍为逐次计时，是否改默认值取决于同程序实际帧率对照。

同程序、同车祸/火焰存档、45 秒预热、每段 15 秒，两轮对照如下：

| 绑定计时 | 静止 FPS | 转镜头 FPS | 图形命令线程 CPU（静止/转镜头，ms/帧） |
| --- | ---: | ---: | ---: |
| 抽样 1/16，第一轮 | 35.86 | 40.77 | 20.92 / 18.99 |
| 逐次，第一轮 | 34.48 | 40.76 | 23.36 / 20.83 |
| 逐次，重复轮¹ | 35.20 | 40.53 | 22.67 / 20.73 |
| 抽样 1/16，重复轮 | 34.55 | 40.13 | 21.10 / 19.30 |

减少的 CPU 开销约 1.4–2.4 ms/帧；没有可重复的最终 FPS 收益，不能称为达成 50–60 FPS。
保留抽样为诊断选项，正常启动仍默认逐次计时。抽样列是估计值，不能当作精确计时。

原因尚未复现或证明解决。测试管线现在每段立即保存 `measurement-phases.json`，
区分游戏未退出与采集器未完成，并在退出后处理超过 15 秒时记录 Python 堆栈。
这些措施用于保存证据和定位停住原因，不会因为疑似卡死自动终止用户游戏。

验证：`bind-timing-shutdown-tests.log` 为 182 项 Python、31 项原生、16 项真实 Vulkan 测试通过，
无失败或跳过；历史 Linux/AppImage 打包模块仍按平台规则排除。

## 回读等待按线程拆分

旧 `buffer_readback_wait_ns` 汇总所有线程的时间，多个游戏线程等待可重叠，
不能将它直接等同于图形命令线程停顿或与 CPU/帧时间相加。
新增 `readback_guest_wait_ns`、`readback_gpu_wait_ns`，从同一计时增量记录，保留旧汇总列。
另外记录异步回读开始/完成命令的往返墙钟时间，以及版本失效后重试次数。
往返时间包含排队与执行，不是该函数的 CPU 时间；开始命令也可能包含同步预读等待，
因此这些列彼此可嵌套，不能全部相加。新增列不改变 GPU 等待、页所有权或粒子正确性策略。

首轮静止实测 35.86 FPS：图形命令线程 22.41 ms CPU/帧，游戏线程回读等待合计 10.00 ms/帧，
图形命令线程回读等待 2.05 ms/帧；开始/完成命令往返 1.05/0.56 ms/帧，重试为零。
源程序、正式存档指纹保持一致，游戏退出 0。

## 自动输入送达验证

审查发现脚本输入读取器在 `fopen` 失败前就缓存文件元数据，临时共享冲突可能让一次输入更新被永久漏掉。
Windows 的 CRT `stat` 还只有秒级时间，不能区分同一秒内同长度的模拟摇杆更新。
修正为使用现有 Win32 高精度文件时间，成功打开文件后才确认更新；没有修改普通手柄映射。
回归用独占打开控制文件再释放，以及同一秒内同长度的 180→181 更新，验证输入最终生效。

实际游戏测试现在对测量区间内的 `input.txt` 检查预期按键和四个摇杆的送达率、样本数及时间覆盖；
缺失或始终中性的转镜头输入直接使区间无效。不能仅凭控制文件已写入或 FPS 有变化确认镜头旋转。
既有历史报告未全部保留完整输入日志，因此不能追认每一轮转镜头都有效；后续收益必须用新验证管线复测。

每段结束录制后保持输入并请求新快照，等待采集完成，保存独立的 `*-post.bmp`。
这部分不计入 FPS，避免只看输入刚开始时的画面。新增时序策略纳入对照校验；
旧报告不能与新策略直接计算收益。新截图仍需人工确认动作和目标场景，送达率不是游戏动作的证明。
